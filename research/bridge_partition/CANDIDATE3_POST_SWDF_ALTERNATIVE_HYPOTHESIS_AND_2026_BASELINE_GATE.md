# Gate after SWDF 176-day physical replay: new-method novelty preflight, not permission to expand prior proxy optimizer

Date 2026-11-21. Historical negative physical gate evidence: https://github.com/AiDevnew168/scale_rag/actions/runs/44908321838.
The exposed SWDF original heldout must not be retuned to rescue the old predicate-only migration approach.

## Precise new question, only as a falsifiable candidate

Instead of optimizing shard contacts while **all** predicate fragments are always transferred, ask whether a **past-only, semantics-safe, risk-budgeted decision about query execution mode** can improve genuinely measured full query response time under workload change, compared to the best independently tuned existing executor/controller.

Action (per query): choose among exact original SPARQL over (A) full predicate materialization, (B) conventional server-side bind/semi-join or FILTER pushdown, (C) original published FedX/Comunica or equivalent compliant federated engine when interface compatible. Only perform state migration/replication if separate total amortized physical cost is included. This is a test question, NOT a novel method claim.

For each request q, compared to a fixed admissible policy pi0, measure:
    measured_reward(q, pi) =
        T_full(pi0,q) - T_full(pi,q) - online_planner_cost(q,pi)
        - audit_feedback_overhead(q,pi),
where full T already contains TCP, source query, coordinator joins, and materialization. If any extra costs were inside T, do NOT double-count them. Whole-horizon benefit subtracts physical switching, deployment, shadow, index, and rollback overhead. The actual past-only controller decisions count; test-selected oracle never counts as deployable profit. Correct original solution bags and blank-node identities are strict eligibility prerequisites.

## 2024-2026 closest baseline warning

- smart-KG+ (https://journals.sagepub.com/doi/full/10.3233/SW-243571) already performs entity/family-based selective partition shipping and reports transfer reduction. Cannot claim query-aware smaller fragments as new.
- FedX (https://rdf4j.org/documentation/programming/federation/) already federates query execution and source selection without manual SERVICE clauses.
- Cost models for heterogeneous RDF federations already existed by 2023 (https://ceur-ws.org/Vol-3443/ESWC_2023_DMKG_paper_7042.pdf). Cannot claim selecting bind join solely on estimated transfer cost as new.
- Fully Inductive Cardinality Estimation (2026, https://arxiv.org/abs/2607.28311) already predicts BGP cardinalities on unseen KGs, including unseen relations. New cross-graph learned cardinality alone is not a claim.
- Strengthening LargeRDFBench for Interoperable Federated SPARQL Evaluation (2026, https://arxiv.org/abs/2608.30465) explicitly diagnoses strict-RDF and oracle-answer discrepancies, provides standards-compliant inputs/results and a FedX-source-selection baseline. Do not claim parser consistency/ground-truth repairs as new, and do not call its static query set a natural temporal workload.

## Prespecified NO-GO conditions for this alternative

1. If a source code comparator plus fair input/output cannot be reproduced, do not make SOTA comparison claims.
2. If a selective executor cannot return semantically legal complete original SPARQL bag answers on genuinely heldout queries including blank nodes and OPTIONAL when applicable, stop. Partial-BGP-only correctness is not full-SPARQL success.
3. If an unchanged FedX/Comunica or smart-KG+ compatible method already matches proposed runtime, bandwidth, p95 and full cost, stop; do not incrementally tune on benchmark test answers.
4. If claimed profits arise only from an after-test oracle, sampled query omission, hidden planning/shadow cost, or old exposed SWDF queries, stop.
5. If there is no fresh natural-time workload with matched RDF snapshot, claim only static benchmark engineering, never on-line workload shift superiority.
6. Report statistical uncertainty by disjoint query family and time blocks, resource-matched storage, networking and index update costs. A few published DIAERESIS samples or 32 LargeRDFBench queries alone cannot justify universal speedup.

## Minimum decisive feasibility

Before code expansion, reproduce unchanged comparator and identical RDF graph on a finite W3C-compliant query batch from the **new cleaned LargeRDFBench artifacts**. Verify original answers against independently produced W3C JSON result sets. Choose a tiny development subset from TRAIN ONLY; reserve independent original query families untouched. A method worthy of further research must actually reduce *total transmitted RDF body bytes* and *end-to-end wall-time* under matched semantics, while its online selection improves over fixed best existing policy after overhead. Do NOT substitute more changes to whole-predicate replica objectives.

**Scientific status:** No demonstrated new algorithmic novelty or journal-positive effect yet. This gate is a disciplined alternative research proposal, not an experiment result.
