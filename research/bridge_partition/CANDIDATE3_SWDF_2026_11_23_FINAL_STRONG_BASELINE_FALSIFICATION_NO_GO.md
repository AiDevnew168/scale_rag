Method C: same 4 workers with safe constant subject/object filtering of original source NTriples lines, still builds NEW per-query temporary RDF Store and executes the same SELECT.
- All **144/144** matched blocks passed the strict independent centralized-vs-sharded conservative SPARQL certification for BOTH distributed arms: **288 successful reference/alternate semantic certifications**. No omissions, timeouts, missing methods, failed semantics, dropped query, rewritten source query or selected-success-only timing result. This is conformance to the implemented *restricted compiler-compatible BGP cohort*, not to all SPARQL 1.1.

## Statistical dependence, cold-path hazards and original source caveats

- The 48 DISTINCT text clusters collapse to only **7 distinct predicate-set families**, family sizes **34, 8, 2, 1, 1, 1, 1**. **42/48** original texts belong to the top two families; do not count 48 independent workload families or project these text-uniform samples to all 4,707 eligible TRAIN source occurrences.
- Text-cluster bootstrap *descriptive sensitivity* for the C-minus-A mean penalty: **[+64.055, +73.770] ms**; predicate-family cluster bootstrap: **[+41.049, +71.416] ms**. These are NOT prospective frequentist confidence intervals: the original cohort and strong baseline results have already been observed; only seven families; the estimator is conditional on this selected original training BGP subpopulation.
- The selected C sample maximum 333.655 ms was **7.32x** the central sample maximum 45.573 ms, consistent with known cold lazy-filter path risk. Previous source-only worker cold/warm physical HTTP study [44920454357](https://github.com/AiDevnew168/scale_rag/actions/runs/44920454357) measured 258.374ms first filtered vs 13.580ms warm and a +25.906 MiB worker RSS rise. The current limited benchmark does NOT fully measure full online cache eviction, model update, memory charges, multi-host scheduling or rollback.
- **SPARQL coverage remains narrow:** previous source-only first88-day analysis found 4,707 eligible original query occurrences, 615 structurally anchored unique texts and 2,929 such occurrences. Only 269 unique texts passed the narrower BGP/engine/constant-filter and supported slice gate. The 48 frozen source texts represent a preselected compiler-compatible subset, not complete arbitrary original SPARQL. Earlier raw 53-day heldout evaluation had a separately proven `PREFIX` target-engine mismatch and is permanently invalid for original all-query economic inference.
- The original RDF graph's temporal alignment with the actual 2014 access-log dates is **unverified**. Four 'workers' here are localhost processes, NOT true multi-host native distributed BGP join execution; the index on workers serves source line fragments, and A has a persistent complete graph index while B/C reconstruct a Store for every query.
- The real published executable AdPart, CostFed, WISE, DIAERESIS and other comparable systems were **not** executed head-to-head, and real WAN latency/throughput/CPU/storage lifetime or node recovery costs were not evaluated. The source version mismatch of the independent 2026 LargeRDFBench 32/40 query archive remains unresolved. Nothing here establishes novel empirical advantage vs strong 2025–2026 published baselines.

## Hard scientific decision and publication

**GO** for engineering fact: source-line-preserving constant filtering saves response-body RDF bytes and improves over this particular inefficient four-worker fetch-everything coordinator. The source semantics are correct for the frozen restricted cohort.

**NO-GO** for the proposed 'competitive faster adaptive distributed RDF/SPARQL sharding' journal-method claim on this measured, memory-fitting, one-host, 304k-triple SWDF graph. A deployable economic controller should choose the static central indexed execution for these selected source texts; an optimizer choosing between B and C cannot surpass A under the observed per-query latency objective. A change in deployment capacity/throughput assumptions would require independent measurement; do not claim a universal impossibility theorem for all distributed RDF data.

**DO NOT** invest further optimizing predicate swaps, naive replica placement, or a superficially new constant filter in this same memory-fitting graph; the strong single-host indexed control already dominates. **DO NOT** recycle the known invalid historical 53-day test split as independent validation. With no original published-system baseline or fresh, version-aligned large real dataset, **journal paper positive novelty and economic-profit GO: FALSE**.

If new publication research is pursued in distributed RDF, register a truly independent workload with graph size sufficient to make single-node complete indexing infeasible under an explicit memory cap, provide actual native distributed server-side join execution and real multi-host measurements, match original AdPart/CostFed-like published baseline implementations, then demonstrate a mathematically new cost/robustness improvement with cold-cache, migration, rollback and changing workload. Even these are *requirements*, not evidence that innovation is likely.
