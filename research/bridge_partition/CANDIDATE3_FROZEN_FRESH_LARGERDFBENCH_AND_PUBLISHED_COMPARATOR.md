# Candidate 3 fresh-domain LargeRDFBench source and original-method baseline gate
**Frozen before opening new dataset/query files — 2026-11-21.**

The existing 2017/2018 Wikidata logs, 2026 WatDiv synthetic data, and FEASIBLE SWDF real-log queries were all inspected during development and are **not confirmatory samples**.

**Candidate entirely new corpus:** LargeRDFBench Interoperable Edition, DOI https://doi.org/10.5281/zenodo.22140177, authors Tam, Saleem and Taelman (2026), linked to original LargeRDFBench. Begin with READ-ONLY file metadata inventory; choose one full authentic RDF graph with compatible SPARQL SELECT queries and published expected answers on the SAME graph version, favoring an originally real Bio2RDF domain such as DrugBank, SIDER or NCBIGene (not an arbitrary graph sample). Do not look at performance/answer outcomes before selection and commit of a strict heldout protocol. If no full compatible graph with >=20 eligible unique query families and >=50 nonempty independent heldout query executions can be identified within a reproducible action, status BLOCKED. Queries may be federated and unsuitable for a four-shard single dataset: count/explain, do not silently rewrite.

**Control frozen:** `candidate3_sparql_semantic_certifier.py`. The ORIGINAL query is timed unchanged. Unordered LIMIT/OFFSET acceptance tests permitted full solution BAG inclusion and exact expected cardinality using a separately evaluated unsliced centralized truth, including a single bijective bnode mapping globally across the answer. False membership, duplicates, missing query answers or an exhausted proof budget => FAIL or INCONCLUSIVE, never PASS. Ordered LIMIT ties and REDUCED are undecidable for this verifier unless exact matching and return INCONCLUSIVE. No after-the-fact removal of failing query families.

**Deployment and evidence:** four distinct indexed Oxigraph worker processes over actual TCP, with real RDF partition bytes, full SPARQL answers and actual migration barrier/index cost. Report no cross-host timing claim when all workers share a VM. Identical hard 10% slack per-shard storage limit and 25MB move/replicate budget. Compare no-move, day0 one/two swaps, replica and hybrid. Lower 95% family-bootstrap net latency after actual migration must beat the best fixed comparable baseline; correctness must be 100% PASS for all required eligible queries, plus no material p95 degradation. Report failed/undecidable queries in denominator.

**Faithful published external competitor:** source `isl/DIAERESIS` at original author commit `22dfe190078973f644f5d6279181e54ec116f6e3`. It compiles under Java 8 with Maven (prior run 44876436118), but requires its own original Spark/HDFS partitioning+query-translating+query-execution path. FULL, UNMODIFIED original three stages must execute successfully for direct runtime comparison and produce query answer correctness and matched-resource cost; a build-only, Java exception, Spark health check or published numbers are NOT an actual baseline comparison. The published engine has different partition/storage semantics and equality of raw byte cap may be impossible; if so mark result incomparable rather than falsely declaring dominance.

**GO/NO-GO:** For paper novelty/economic superiority GO requires query correctness, truly new independent real dataset full original source and independently sampled workload, author-method baseline runnable and matched conditions, measured net positive 95% lower bound vs strongest baseline, and ideally multiple chronological shifts. Otherwise BLOCKED/FAIL per exact gate. No post-hoc threshold or query selection.
